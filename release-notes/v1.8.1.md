**Bug-fix release, and one of these is serious.** If you download to a NAS or
network share, **every download has been failing since v1.8.1's grandparent,
v1.6.1** — even though the files were arriving correctly. Upgrade.

Nothing here changes how you use Vidshelf. No new settings, no migration.

## Downloads to a network share were reported as failed (since v1.6.1)

If your media folder is a NAS/SMB share, downloads have been ending like this:

```
PermissionError: [Errno 1] Operation not permitted
```

**Your files were fine.** The video was fully downloaded and correctly copied to
the share before the error hit — the failure was in the last cosmetic step,
copying the original file's timestamp across. But because that step threw:

- the download was shown as **failed**, though it had actually succeeded
- the temporary local copy was never cleaned up, so **`downloads/` filled with
  duplicates** — 2.6 GB on the machine this was diagnosed on
- the video was never recorded as downloaded, so it would be **fetched again**
  on the next check

The cause was v1.6.1, which tightened container permissions by dropping all Linux
capabilities. That was the right change, but it removed the specific privilege
needed to set a timestamp on a file the share reports as owned by someone else.
Copying the timestamp is now optional, which is what the project's own notes
always said it should be.

### What you should do after upgrading

1. **Check `downloads/` for leftovers.** Vidshelf now clears these itself (see
   below), but only from folders it can prove are staging areas — anything in
   `downloads/` itself is left for you to review.
2. **Videos that "failed" but are on your NAS aren't in the download history**,
   so a channel check may fetch them again. Either let it (you'll get a
   duplicate) or delete the NAS copy first and let it re-download cleanly.

## Leftover files are now cleaned up automatically

On startup, Vidshelf removes yt-dlp's temporary files — the separate video/audio
fragments it merges, plus `.part` and `.ytdl` files — from its download folders.
Nothing younger than three hours is touched.

**It is deliberately conservative about finished videos.** Complete files are
only removed from folders that are staging areas *by design* — currently just
`downloads/music_videos`, which every music-video download copies out of.
`downloads/` itself is never cleared of finished videos, because it's the default
media destination and may hold files from an earlier configuration of yours.
If you have leftovers there, you decide what goes.

## Channel monitoring could stop working, silently and permanently

Downloads interrupted by a container restart were left marked as still running,
forever. Vidshelf skips a scheduled check when too many downloads look like
they're already in progress — so once **20** of these accumulated, automatic
channel checks **stopped happening entirely**, with no error and nothing in the
log to say why.

Twenty restarts mid-download is unremarkable over a few months. If your channel
monitoring seemed to have quietly stopped, this is likely why.

Interrupted downloads are now closed out at startup and show as *Interrupted* in
the Downloads list.

## Smaller fixes

- **Download history is capped** at 200 finished entries. It previously grew for
  the life of the install, and the whole list was re-sent to your browser every
  two seconds with the Downloads tab open.
- **Retrying a download twice in quick succession** could overwrite the first
  attempt's record instead of creating a second one.
- **A hand-edited `config.json`** missing a channel's `download_path` returned a
  500 error instead of falling back to the default.
- **Two internal tables grew without limit** — the failed-login tracker and the
  search caches. Both are now bounded.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

No recreate needed. Interrupted downloads from previous runs are tidied up
automatically on first start.
