Maintenance release. No user-facing changes — this exists to exercise the release
pipeline after six dependency updates.

## Dependency updates

| Package | Change |
| --- | --- |
| `certifi` | 2026.6.17 → 2026.7.22 |
| `actions/setup-python` | 5.6.0 → 7.0.0 |
| `docker/login-action` | 3.7.0 → 4.6.0 |
| `docker/metadata-action` | 5.10.0 → 6.2.0 |
| `docker/build-push-action` | 6.19.2 → 7.3.0 |
| `peter-evans/create-pull-request` | 7.0.11 → 8.1.1 |

Five of those are major version bumps, but all carry the same underlying change:
Node 24 as the default runtime plus an internal refactor. No inputs were renamed
and no behaviour changed. All CI jobs run on GitHub-hosted runners, so the
associated runner requirement is met automatically.

## Why a release for dependency updates

Three of those actions run only in the image-publishing job, which never executes
on a pull request. A release is the only thing that actually exercises them —
without one, the next release you cared about would have been the experiment.

## Upgrading

`docker compose pull && docker compose up -d`. The application code is unchanged
from v1.4.0; only the build toolchain and the CA bundle moved.
