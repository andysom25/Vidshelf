**Every download above 360p was failing partway through with `HTTP Error 403: Forbidden`. This release fixes it — but requires one change to your `docker-compose.yml` if you're not using `update.ps1`.**

## Downloads failing with HTTP 403: Forbidden

Starting mid-August 2026, YouTube tightened its anti-bot enforcement to the
point that downloads above 360p would start normally — real progress, real
speeds — and then die a few seconds and megabytes in, every single time. This
wasn't a bug introduced by Vidshelf; it was YouTube requiring things yt-dlp's
stable releases hadn't caught up to yet, stacked with an unrelated cookies
problem that made it hard to see what was actually wrong.

Three things were needed, and all three are now handled automatically:

- **A JS runtime.** yt-dlp needs to execute YouTube's own signature-challenge
  code to get valid download URLs. The Docker image now bundles
  [Deno](https://deno.land) for this.
- **A PO Token provider.** YouTube's current enforcement requires a
  Proof-of-Origin token to keep streaming past the first few seconds. A new
  companion container, `bgutil-provider`, generates these — see below for
  what you need to do.
- **A yt-dlp build that isn't stuck behind YouTube's current rollout.**
  Every stable yt-dlp release through `2026.7.4` hits this wall; a verified
  nightly build doesn't. `requirements.txt` is pinned to that specific build
  until a stable release catches up — see `REFERENCE.md` if you're curious
  about the exact chain of evidence, or want to know when it's safe to move
  back to a stable pin.

Cookies got a real fix too: **Settings → System Health now checks that
`data/cookies.txt` actually contains a YouTube login**, not just that a file
exists there. A cookies.txt exported from the wrong browser tab used to
report "available" while doing nothing.

## Action required: add `bgutil-provider` to your `docker-compose.yml`

Pulling the new image alone won't do this — Compose only creates services
listed in your own file. Add:

```yaml
services:
  bgutil-provider:
    image: brainicism/bgutil-ytdlp-pot-provider:latest
    container_name: bgutil-provider
    restart: unless-stopped
```

and add `depends_on: [bgutil-provider]` to the `vidshelf` service, then:

```bash
docker compose up -d
```

Skipping this doesn't break anything immediately — 360p downloads still
work — but everything above that will keep failing with HTTP 403 until it's
added. The full example is in the README's Quick Start section.

`docker compose up -d` creates any newly-defined service automatically, so
`update.ps1` on Windows needs no special flag for this — just add the block
above to `docker-compose.yml` first, then run it as usual.

## Upgrading

```bash
docker compose pull && docker compose up -d      # after adding bgutil-provider above
docker compose up -d --build                     # building from source
```

Or on Windows: `.\update.ps1`.

No config migration needed — `data/` is untouched. If you don't already have
a `data/cookies.txt` with a real YouTube export, age-restricted and
members-only videos will still be skipped (unchanged from before), but that
no longer affects downloads in general the way the 403 issue did.
