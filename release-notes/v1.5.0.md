Adds the automation Vidshelf was described as having but didn't: **nothing ran on
a schedule.** A channel set to *New Only* downloaded nothing until you clicked a
button.

Three features, all **off by default** — existing installs behave identically
until you enable them in Settings.

## Automatic channel monitoring

Checks your channels on a timer (default hourly) and downloads anything new.

- Only channels set to **New Only** or **All Videos** are checked. **Manual**
  channels are never touched.
- Videos you already have are **always** skipped, so a channel on *All Videos*
  won't re-download its back catalogue on every pass.
- A **Check now** button runs a pass immediately.
- One unreachable channel doesn't stop the others.

## Notifications

Sends a message when something happens while you're not watching. Paste a
Discord or Slack webhook, an ntfy or Gotify URL, or any endpoint accepting a JSON
POST — the type is detected from the URL.

Choose which events you want: failed downloads, check results, retention sweeps,
or every completed download. **Completions are off by default** — a bulk download
would otherwise send dozens of messages.

Your webhook URL is never sent back to the browser once saved, since it usually
embeds a secret.

## Storage retention

Deletes the oldest videos once an artist folder holds more than you want to keep.
This is the only feature that deletes media, so it always previews first and
requires explicit confirmation.

**Pruned videos are not re-downloaded.** Retention removes files but keeps the
download history on purpose — otherwise monitoring would re-fetch exactly what
retention just removed. Clearing download history is what makes them eligible
again.

It refuses to run if your media root contains no artist folders, on the
assumption the volume isn't mounted. Check `docker exec vidshelf df -h` if you
see that.

## Under the hood

- 51 new tests, including source-level invariants for bugs that only appear
  against a real network mount and so can't be caught by a normal test.
- The `_is_safe_download_url` SSRF guard now has test coverage; it previously had
  none.

## Upgrading

`docker compose pull && docker compose up -d`, or `up -d --build` from source.
Nothing to migrate.
