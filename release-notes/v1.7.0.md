**Security release.** Two API endpoints that did not require a login now do.
**Upgrading is recommended.**

Nothing changes in how you use Vidshelf — no new settings, no migration, and the
Swap Artwork feature works exactly as before.

## Two artwork endpoints were reachable without logging in

`/api/artwork/search_noauth` and `/api/artwork/swap_noauth` accepted requests
from anyone who could reach Vidshelf's port. Both now require a session.

What that allowed, for anyone able to reach the port:

- **Running artist artwork searches.** These fan out to TheAudioDB, Fanart.tv,
  MusicBrainz and Wikimedia — using *your* Fanart.tv API key if you configured
  one.
- **Replacing artwork.** `folder.jpg`/`poster.jpg` could be overwritten in any
  artist folder you already had, and your Plex collection's artwork updated using
  your stored Plex token.

It was bounded — no way to escape into other directories, no new folders, and
image URLs still went through the SSRF guard — but it should not have been open.

**Who is affected:** if Vidshelf is only reachable on your LAN, the practical
exposure is other devices on your own network. If you have ever port-forwarded it
or put it on a public interface without a reverse proxy requiring auth, treat it
as having been open to the internet, and consider rotating your Fanart.tv key.

### Honest note on why this took until now

Earlier releases documented these endpoints as *deliberately* unauthenticated, on
the stated grounds that requiring a login "would break whatever consumes it".
That was never verified. The only thing calling them was Vidshelf's own
dashboard, which is already logged in — so there was nothing to break, and the
reason for leaving them open had never been true.

## If you call the API yourself

Both endpoints now return **401** instead of a result when called without a
session. This is the one change that could break something you have built.

- New canonical paths: **`/api/artwork/search`** and **`/api/artwork/swap`**.
- The old `_noauth` paths still exist as aliases and behave identically, so you
  get a clear `401` rather than a confusing `404`. They may be removed in a
  future release — please move to the canonical names.
- To call them from a script, log in first and reuse the session cookie.

## Also

The test that was supposed to catch this had three separate blind spots, all now
fixed:

- it treated only `HTTP 200` as a failure, so an endpoint that rejects a *missing
  parameter* before checking your session looked correctly guarded
- it only ever issued `GET` requests, so POST-only endpoints were never checked
- its route helper silently skipped any endpoint that does not accept `GET`, so
  adding POST to the check was not enough on its own

The rule now is stricter: an endpoint must refuse an anonymous caller *before* it
looks at anything else, and a `400` counts as a failure. All 57 other endpoints
already met it.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

No recreate needed this time — nothing changed about the container itself.
