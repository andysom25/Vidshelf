Control over what downloads, and the ability to stop one. v1.5.x gave you
unattended automation; this release gives you the handles for it.

## Cancel and retry downloads

Downloads previously ran to completion or failure with no way to intervene — you
could start one but never stop it, and a failed download had to be found and
re-triggered by hand. Now every download row has a button:

- **Cancel** a queued or running download. A queued one stops immediately; a
  running one stops within about a second.
- **Retry** anything that failed or was cancelled, without hunting for the video
  again.

A cancellation is recorded as *Cancelled*, not as an error, and does **not** send
a "download failed" notification — you asked for it.

Cancelling is cooperative rather than a hard kill: the download unwinds through
its own cleanup instead of a worker being terminated mid-write, because a
half-written file landing on a network share is a mess this project has paid for
before. Retrying creates a new entry rather than overwriting the failed one, so
the history of what went wrong stays honest.

## Per-channel quality cap

Every channel now has a **Max** selector — best available, 4K, 1440p, 1080p or
720p — next to its download mode.

Previously the format selection was hardcoded, so monitoring a 4K channel
unattended meant 4K files whether you wanted them or not, costing both disk and a
CPU-heavy re-encode per file. The cap applies to every fallback branch, so asking
for 1080p can't be quietly overridden by a channel that only publishes AV1 at
2160p.

It's per channel on purpose: the reason to cap is usually one specific channel,
and capping everything to deal with that would needlessly downgrade the rest.
Leave it on *Best available* and nothing changes.

## Cookies now actually work

A `cookies.txt` could sit in the install directory indefinitely while **nothing
ever passed it to yt-dlp** — so age-restricted and members-only videos failed
with no indication why.

Drop a yt-dlp-format `cookies.txt` into your `data/` directory and it's used for
every download. **Settings → System Health** now shows whether one was found, so
this can't be silently wrong again.

## Bug fixes

**The dashboard showed the same number twice.** "Videos Available" and
"Downloads" were computed from the *identical expression*, so they were always
equal and one of the four cards told you nothing. The first card is now **New
Available** — videos seen on your channels that you haven't downloaded, which is
the number that answers "is there anything to fetch". It reads `--` until an
automatic check has run, rather than claiming `0` when nothing has looked yet.

**The sidebar said "beta".** It hasn't been true since v1.0.0. Removed; the
version is already shown at the bottom of the sidebar.

## Upgrading

`docker compose pull && docker compose up -d`, or `up -d --build` from source.

Nothing to migrate, and no behaviour changes unless you use the new controls:
quality caps default to *Best available* (identical to previous behaviour), and
cookies are only used if you provide a file.
