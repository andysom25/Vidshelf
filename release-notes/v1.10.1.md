**Bug-fix release. Upgrade if you use the Music Videos search.**

Nothing to migrate, no settings changed.

## Music Video search could hang and then fail with a message that meant nothing

Searching for an artist sometimes ended in:

```
Failed to search: Failed to fetch
```

That text is the browser's own wording for a connection that died. It named
nothing, pointed at no layer, and looked exactly like an application crash — the
first report of it sent us looking at the wrong thing entirely.

**What was actually happening.** Vidshelf asks YouTube for a quality label
("1080p", "4K") for each of the 9 results on a page. Those 9 lookups ran **one
after another**, and each one used yt-dlp's default network settings: **no socket
deadline at all, and 10 retries with escalating backoff.** Those defaults are
right for downloading a file, where a retry is the difference between getting the
video and not. They are wrong for anything a browser is waiting on — one throttled
response held the entire request open until the browser gave up.

So the search worked fine most of the time and failed unpredictably when YouTube
was slow, which is the worst possible failure shape: nothing to reproduce, and a
message that blames the app.

**Three changes:**

- **Every metadata lookup is now bounded** — a 15-second socket timeout and a hard
  retry cap, applied through one shared helper so a future lookup cannot be added
  without them.
- **The 9 lookups run concurrently**, and each one's failure is contained. A
  lookup that fails or overruns yields "unknown" for that single video; it can no
  longer take the search results down with it. **Side effect: the search is
  roughly twice as fast** — measured 6.7s where it previously took about 13s.
- **When something does go wrong, the message says what.** A timeout now says it
  timed out, how long it waited, and to check your reverse proxy's read timeout if
  you use one. A dropped connection says the connection dropped rather than the
  search failing, and suggests `docker ps`. A server error shows the status code
  instead of a JSON parser complaint about the proxy's HTML error page.

**This bug was not introduced in v1.10.0.** The search code is byte-identical in
v1.9.2 and every release before it, back to when the feature shipped. If you saw
this on v1.10.0, you would have seen it on any earlier version under the same
conditions.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

Or on Windows, `.\update.ps1`. No recreate needed.
