Fixes six gaps in the v1.5.0 automation features, found by auditing them rather
than by hitting them in use. No new features; if you had automatic monitoring
switched off, nothing here changes your setup.

## Retention now actually protects unattended downloads

**Retention only ever ran when you clicked the button.** v1.5.0 shipped it as a
manual preview-then-delete flow, so monitoring could run unattended for weeks
with nothing bounding disk use — the exact problem retention exists to solve.

There is now an **Automatically prune after each check** option in
Settings → Storage Retention. It's a second, separate opt-in on top of
*Enable retention*, so upgrading never starts deleting media by surprise.

**Retention swept the wrong directory for channel downloads.** It only looked at
the music-video root, but YouTube channel videos land under your Plex base path
or a per-channel path. Monitoring downloaded to one place and retention pruned
another. It now sweeps every configured media root.

An unreadable or unmounted root is now skipped with a recorded reason instead of
stopping the whole sweep, so one offline share can't disable pruning everywhere.

## Three brakes on unattended growth

None of these were present in v1.5.0, which would happily queue work faster than
it could ever finish:

- **Free-space floor** — set a minimum in GB and checks stop queuing downloads
  when the destination drops below it. Off by default.
- **Queue-depth limit** — if downloads are already backed up, a check is skipped
  entirely rather than adding more. Defaults to 20 in flight.
- **Listing cap** — a check now considers only the most recent N videos per
  channel (default 50) instead of a channel's entire history.

## Repeatedly failing channels back off

A channel that keeps failing — deleted, renamed, region-blocked — used to be
retried and *notified about* on every single check. It now backs off
exponentially (1, 2, 4, then 8 checks) and resets on the first success.

## Performance: a check no longer re-reads its history per video

The biggest fix, and invisible from the outside. Each check re-read and re-parsed
the entire download-history file **once per video considered** — measured at 500
file reads for a 500-video channel, on every channel, on every check. It now
reads once per channel.

If you have large channels, checks will be noticeably faster and much lighter on
disk.

## Also

- The Settings panel gained the new options, and `settings.png` in the README was
  recaptured to show them.
- Release notes are now authored per release rather than auto-generated. v1.4.1
  and v1.5.0 shipped with notes that just linked their pull request; both have
  been backfilled.
- 16 new tests covering every fix above, including one that proves the
  per-channel read happens once and one that proves a failing retention sweep
  can't take a check down with it.

## Upgrading

`docker compose pull && docker compose up -d`, or `up -d --build` from source.
Nothing to migrate. All automation remains off by default.
